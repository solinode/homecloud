# Pulumi on HomeCloud

A small Pulumi program (TypeScript) written with the stock `@pulumi/aws` provider. Nothing in `index.ts`
is HomeCloud specific: the provider is pointed at HomeCloud by the environment and two settings in
`Pulumi.yaml`, so the same program deploys to AWS.

What it builds:

| Resource | Notes |
| --- | --- |
| S3 bucket and object | `forceDestroy`, so `pulumi destroy` empties it |
| DynamoDB table | on-demand, hash key `id` |
| SQS queue | 60 s visibility timeout |
| IAM role | trusted by `lambda.amazonaws.com`, with `AWSLambdaSQSQueueExecutionRole` and an inline `dynamodb:PutItem` policy |
| Lambda function | Node.js 24, inline code, `loggingConfig` pointing at the log group below |
| Event source mapping | the queue triggers the function, which writes each message to the table |
| CloudWatch log group | declared so `pulumi destroy` removes it |

Verified with Pulumi CLI 3.268.0, `@pulumi/aws` 7.50.0 (provider plugin 7.50.0), Node.js 24 and HomeCloud
0.5.x built from `main` (Node.js 24 functions and `loggingConfig` need it). `pulumi up`, `pulumi preview`
(no changes), `pulumi refresh` (no changes) and `pulumi destroy` all run clean on a fresh install, over
HTTP and over HTTPS (`--tls-self-signed`).

## Prerequisites

* A running HomeCloud (`homecloud serve`).
* The Pulumi CLI and Node.js 18 or newer. No Pulumi account is needed: state is kept in a local
  directory.

## Run it

```bash
eval "$(homecloud aws-env)"                         # AWS_ENDPOINT_URL, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_REGION
export PULUMI_BACKEND_URL=file://$HOME/.pulumi-local   # local state; or `pulumi login --local`
export PULUMI_CONFIG_PASSPHRASE=                    # no secrets in this program

cd examples/pulumi/basic
npm install
pulumi stack init dev
pulumi up --yes                                     # about half a minute
```

### Provider settings, and why

* `AWS_ENDPOINT_URL` (from `homecloud aws-env`) sends every AWS call to HomeCloud. The provider reads
  it like the AWS CLI does, so no per-service endpoint list is needed.
* `aws:s3UsePathStyle: true` (in `Pulumi.yaml`): HomeCloud serves buckets by path, so bucket names need
  not resolve as host names.
* `aws:region: us-east-1` (in `Pulumi.yaml`): HomeCloud's region.
* No `skipCredentialsValidation`, `skipRequestingAccountId` or `skipMetadataApiCheck` is needed:
  HomeCloud implements STS, so the provider's startup checks pass unchanged.
* With HTTPS, `homecloud aws-env` also exports `AWS_CA_BUNDLE`, which the provider honors.

If you prefer an explicit `aws:endpoints` block in the stack configuration instead of the environment
variable, list every service the program uses **plus `sts` and `s3control`** (the provider reads bucket
tags through S3 Control), and set `aws:skipCredentialsValidation`, because Pulumi's own credential check
ignores `aws:endpoints` and asks the real AWS STS:

```bash
for s in cloudwatchlogs dynamodb iam lambda s3 s3control sqs sts; do
  pulumi config set --path "aws:endpoints[0].$s" "$AWS_ENDPOINT_URL"
done
pulumi config set aws:skipCredentialsValidation true
```

Use a host name for the endpoint, not an IP address: S3 Control puts the account ID in front of the host
(`123456789012.localhost` resolves, `123456789012.127.0.0.1` does not). `homecloud aws-env` already prints
`localhost` for a local server.

## Check that it works

```bash
aws s3 cp "s3://$(pulumi stack output bucketName)/README.txt" -        # uploaded by Pulumi
aws sqs send-message --queue-url "$(pulumi stack output queueUrl)" --message-body '{"order":1}'
aws logs tail "$(pulumi stack output logGroupName)" --since 5m          # ... INFO order received: {"order":1}
aws dynamodb scan --table-name "$(pulumi stack output tableName)" --query 'Items[].body.S'
```

A second `pulumi preview --expect-no-changes` and a `pulumi refresh` report no changes.

## Tear down

```bash
pulumi destroy --yes
pulumi stack rm dev --yes
```

## Notes

* The provider waits for SQS queue attributes to settle after creating and deleting a queue, so those
  two steps take about 25 seconds each, as they do on AWS.
* The log group is declared in the program. Lambda creates its group on first invoke and, on AWS as on
  HomeCloud, leaves it behind when the function is deleted, so `destroy` would otherwise not leave the
  account empty.

## Fixed in HomeCloud while verifying this example

* Lambda accepts the `nodejs24.x`, `python3.14` and `java25` runtimes.
* Lambda supports `LoggingConfig` (custom log group, `Text`/`JSON` format and log levels); it was
  ignored before.
* The self-signed certificate of `--tls-self-signed` covers `*.localhost` and `*.<public-host>`, so S3
  Control calls (`<account>.localhost`) verify over HTTPS. A certificate generated by an earlier version
  is kept: delete `<data-dir>/tls/` to get a new one.
