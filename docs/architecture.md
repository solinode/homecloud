# HomeCloud architecture

HomeCloud is a single Go binary (`homecloud`) that is both the server and the CLI. `homecloud serve` starts one HTTP server that hosts:

- the REST API under `/api/v1`, one package per service in `cli/internal/svc/`;
- the web console, a static Next.js export embedded into the binary at build time;
- public data-plane endpoints: function URLs (`/lambda-url/...`), HTTP APIs (`/apigw/...`) and static websites (`/website/...`).

Every resource that needs a process (instances, databases, caches, functions, the S3 server) runs as a **Docker container**. HomeCloud labels everything it creates with `homecloud.managed=true`, `homecloud.service` and `homecloud.resource`, and never touches objects without those labels, so it can share a Docker host with anything else.

```
            browser / homecloud CLI / curl / AWS SDK (S3)
                              │
               ┌──────────────▼───────────────┐
               │   homecloud serve  (:8080)   │
               │  httpx router ─ IAM check ─ CloudTrail
               │  ┌─────┬─────┬─────┬──────┐  │
               │  │ ec2 │ s3  │ rds │lambda│… │   state.json, dynamodb.db,
               │  └──┬──┴──┬──┴──┬──┴──┬───┘  │   logs/, trail/, sqs/, snapshots
               └─────┼─────┼─────┼─────┼──────┘
                     │ Docker Engine API │
      ┌──────────────▼─────▼─────▼─────▼─────────────────┐
      │ VPC network hc-vpc-… (10.88.0.0/16, bridge)       │
      │  i-0abc (10.88.0.4)  pg1.rds.internal  s3.internal │
      │  hc-lambda-fn        cache1.elasticache.internal   │
      └───────────────────────────────────────────────────┘
```

## Request path

1. `httpx.Router` matches the route. Each route declares an IAM action (e.g. `ec2:RunInstances`) and optionally a resource ARN template (`arn:aws:s3:::{bucket}`).
2. `iam.Service.Authenticate` resolves the caller from a console session token (`hcs_…`) or an access key (`<id>:<secret>`). Secrets are stored as SHA-256 hashes; console passwords as bcrypt.
3. The caller's effective policies (attached, inline, and via groups) are evaluated like AWS: an explicit `Deny` wins, otherwise any matching `Allow` grants, otherwise deny. The root user bypasses checks; `sts:*` identity calls are always allowed.
4. The handler runs. Mutating calls and denied calls are appended to the CloudTrail log (`trail/YYYY-MM-DD.jsonl`, 90-day retention).

## State

| What | Where |
| --- | --- |
| Resource records (users, instances, queues, rules, …) | `state.json`, a set of JSON collections written atomically on every change (`internal/store`) |
| DynamoDB items | `dynamodb.db` (embedded bbolt), one bucket per table, keys encoded to preserve sort order |
| SQS messages | in memory, snapshotted to `sqs/<queue>.json` every 2 s and on shutdown |
| Metrics | in memory (24 h per series), snapshotted to `metrics.json` |
| Logs | `logs/<group>/<stream>.jsonl`; container log groups (`/hc/<service>/<id>`) read Docker logs live |
| Lambda code | `lambda/<function>.zip` ($LATEST), `lambda/versions/<function>/<n>.zip`, `lambda/layers/<layer>/<n>.zip` |
| Database snapshots | `rds-snapshots/<snapshot>.bak` (engine-native dumps) |
| Secrets | encrypted in `state.json` with AES-256-GCM under `master.key` |
| Object data | the `homecloud-s3-data` Docker volume behind MinIO |

The data directory defaults to `~/.homecloud` (override with `--data-dir` or `HOMECLOUD_DATA_DIR`). Back it up together with the Docker volumes whose names start with `hc-` and `homecloud-`.

## Services

**VPC.** A VPC is a Docker bridge network spanning its CIDR. Subnets are ranges of it, and IPs are allocated per resource (AWS-style: the first four and last address of each subnet are reserved), so every instance, database and function gets a stable private IP and DNS aliases. A default VPC (`10.88.0.0/16` or the next free `/16`) is created on first start. Security groups decide which ports are published on the host when a resource launches and, inside the VPC, which resources may talk to each other (next paragraph).

**EC2.** An instance is a container with CPU quota and memory limits taken from its instance type. OS images (Ubuntu, Debian, …) boot a small init script that runs user data once and then idles, so the instance behaves like a VM that stays up; application images (e.g. `ami-nginx`) run their own entrypoint. Instance metadata is written to `/var/lib/homecloud/instance.json`. Volumes are named Docker volumes. "Create image" commits the container into `homecloud/ami:<id>`. The browser terminal is a WebSocket bridged to `docker exec` with a TTY.

**EC2 VM instances.** The catalog also has VM images (`ami-ubuntu-24-04-vm`, `ami-debian-12-vm`, marked "(VM)", `virtualization: "vm"`, EC2 hypervisor `kvm`): the official cloud images for the Docker host's architecture, pinned to a release and verified by SHA-256/512 after download, kept in a HomeCloud-managed Docker volume (`hc-vm-images`) so each is downloaded once. Launching one starts a **VM container**: a Docker container, built locally on first use from `cli/internal/svc/ec2/vm/runner.Dockerfile` (Debian pinned by digest with QEMU, passt, UEFI firmware, genisoimage, tagged by content hash), that runs a single QEMU process. The container is attached to the instance's VPC network with the instance's private IP exactly like a container instance, so everything that is per container keeps working unchanged: VPC addressing, DNS, the metadata service (a route in the container's namespace), security groups (iptables in the container's namespace, which see the guest's traffic because the guest lives behind the container's sockets) and published ports.

| | Container instance | VM instance |
|---|---|---|
| Kernel, init | the host's; a small init script or the image's entrypoint | the guest's own; systemd, cloud-init |
| Root disk | writable layer of the container | qcow2 overlay on the cached cloud image, in the root EBS volume (`/dev/xvda`, sized by the root block device mapping, default 8 GiB) |
| Networking | the container's veth | the same veth; passt gives the guest the container's address, gateway and routes and forwards every inbound TCP and UDP port to it |
| Login | `docker exec` (terminal, run-command) | SSH with the key pair (the image's default user `ubuntu` or `debian`); the browser terminal is the serial console, run-command goes through the guest agent |
| User data, key | boot script, `/root/.ssh/authorized_keys` | cloud-init NoCloud seed ISO (`cidata`): instance ID, hostname, the key pair's public key, user data as sent (script, `#cloud-config`, ...) |
| Console output | container log | the guest's serial console (the container log) |
| Stop, reboot | container stop, restart | ACPI power button through QMP, then a kill after a timeout; reboot is stop + start of the same container |
| Extra volumes | Docker volumes mounted at a directory (`/mnt/sdf`) | Docker volumes holding a sparse raw `disk.img`, attached as virtio disks (see below) |
| Snapshots, images | copy of the volume's files; `docker commit` | root disk flattened (`qemu-img convert`) into a standalone qcow2; other volumes copied |
| Terminate | container and volumes removed | container removed; root volume removed unless `DeleteOnTermination` is false |

**VM disks.** The root volume (EBS device `/dev/xvda`, mounted at `/vm` in the VM container) holds `disk.qcow2`, an overlay on the cached cloud image (or a standalone copy, for an instance launched from an image made from an instance). Any other volume is mounted at `/disks/<volume ID>` and holds `disk.img`, a sparse raw image of the volume's size, created on first use and grown at the next start if the volume was enlarged. The guest sees them as virtio disks in the order of their EBS device names (`/dev/sdf` before `/dev/sdg`): `/dev/vdb`, `/dev/vdc`, and so on (the root disk is `/dev/vda`; the cloud-init seed is the last one), and always as `/dev/disk/by-id/virtio-<first 20 characters of the volume ID>`, which is the name to use in `fstab`. `BlockDeviceMappings` at launch and `AttachVolume`/`DetachVolume` work; the root volume cannot be detached. Docker cannot add a mount to a running container, so there is no hot-plug: attaching or detaching a volume rebuilds the VM container, which shuts the guest down gracefully and boots it again with the new set of disks (the volume shows `attaching`/`detaching` until then). The NIC sits at a fixed PCI slot so its name in the guest does not change when disks come and go.

`CreateSnapshot` of a root volume and `CreateImage` of an instance flatten the overlay with `qemu-img convert`, so they never depend on the cloud image cache, the instance or its volume. A running guest's disk is read while it is open (crash-consistent, like an EBS snapshot of a running instance); stop the instance first for a clean image. An image made from an instance is a Docker volume (`hc-<ami ID>`) holding that disk; `RunInstances` from it copies the disk into the new instance's root volume (so deregistering the image leaves running instances alone), at least as large as the image's disk, on a host of the same architecture. Snapshots restore to volumes and volumes attach as data disks as before.

`homecloud backup` archives a VM's root volume as a standalone qcow2 (the volume carries the label `homecloud.vm-root`, and the server hands such volumes to a flatten step while the VM container is paused); the image cache is left out. A restore brings volumes back but no containers: when HomeCloud then finds a VM instance whose container is gone but whose root volume exists it recreates the container and leaves the instance `stopped`, instead of terminating it as it does for container instances; starting it boots the restored disk.

The guest runs with `-accel kvm -cpu host` when the Docker host has `/dev/kvm` (probed once by creating a container with the device; `HC_VM_ACCEL=kvm|tcg` overrides) and is otherwise emulated (`-accel tcg`, logged as a warning). The instance reports `virtualization: "kvm"` or `"emulated"`. Docker for Mac (OrbStack, Docker Desktop) has no `/dev/kvm`, so guests there are emulated; a native macOS `hvf` guest is not implemented. `-smp` and `-m` come from the instance type, and the container's limits are a little higher for QEMU's own overhead. An instance is `pending` until the guest is up: cloud-init's final message (or a login prompt for a while) on the serial console, with a generous timeout (30 minutes emulated). Changing security-group rules that change which ports are published rebuilds the container like for container instances; the disk is in the volume, but the guest is shut down and boots again. **Security trade-off.** passt sandboxes itself (user, mount and pid namespaces, `pivot_root`, then runs as `nobody`). Docker's default seccomp profile blocks that, so the VM container uses a custom profile: Docker's default (moby v27.4.1, embedded in `vm/seccomp-docker-default.json`, deny by default) plus an unconditional allow for exactly `unshare`, `mount`, `umount2` and `pivot_root`, the minimum found by removing each syscall in turn until passt failed. Everything else the default profile forbids (`bpf`, `keyctl`, `kexec_load`, module loading, `perf_event_open`, ...) stays forbidden, and the kernel still checks capabilities, which passt only has inside the namespaces it creates. AppArmor is not narrowed: on Ubuntu hosts the `docker-default` profile denies the remount and `pivot_root` of passt's sandbox (verified on Ubuntu 24.04 with `kernel.apparmor_restrict_unprivileged_userns=1`), and a narrower profile would have to be loaded on the host, which HomeCloud (a Docker client) cannot do, so the VM container runs with `apparmor=unconfined`. An administrator who loads a profile allowing mount, umount and `pivot_root` inside user namespaces can name it with `HC_VM_APPARMOR`. The container still gets only Docker's default capabilities, no `SYS_ADMIN`, no privileged mode and no host devices except `/dev/kvm` when accelerated; the trust is that of a root process in a container without MAC confinement running QEMU and passt, so use VM images only where you would accept that. passt also opens a socket per forwarded port, so the VM container's open-file limit is raised to 1048576 (Docker's default on some hosts is 65536 or 1024, which made passt fail with "Too many open files"). Instances report `vm_network: "passt"` or `"user"`. If passt cannot start (for example a host whose security modules forbid the user namespace), or when the server runs with `HC_VM_NET=user`, the container falls back to QEMU's user-mode networking: the guest then sits behind NAT at 10.0.2.15, still reaches the metadata service and DNS, and only the TCP/UDP ports that the instance's security groups open (at most 64, whatever their source) are forwarded to it; a rule that opens another port rebuilds the container (the guest reboots), for the automatic fallback too; the server logs why passt failed.

**Guest agent, run-command, terminal, metrics.** The command line adds a virtio-serial port `org.qemu.guest_agent.0` backed by a socket in the VM container (`/run/qga.sock`), and cloud-init's vendor-data (a script, so it survives a user-data `packages:` or `runcmd:`) installs and starts `qemu-guest-agent`. *Run-command* (`POST /api/v1/ec2/instances/{id}/commands`, `ssm:SendCommand` as for containers) sends `guest-exec` for `/bin/sh -c` (wrapped in the guest's `timeout(1)` so the command is killed at its timeout; status `TimedOut`) and polls `guest-exec-status` for stdout, stderr and the exit code. Each agent call is a `docker exec` of `socat` into the VM container that does the `guest-sync-delimited` handshake first; QEMU serves one agent client at a time, so calls to one guest are serialized. The agent needs the image's network on first boot to install it (images are Debian/Ubuntu); until it is up run-command fails with a clear error. The *browser terminal* cannot be a shell through the agent (`guest-exec` is not interactive), so it attaches to the guest's **serial console**: the serial port is a QEMU socket chardev (`/run/serial.sock`) with `logfile=/dev/stdout`, which tees everything the guest prints into the container log so `GetConsoleOutput` and the boot-ready detection are unchanged whether or not a terminal is attached. The terminal WebSocket runs `docker exec -t ... socat -,raw,echo=0 UNIX-CONNECT:/run/serial.sock`; the user presses Enter and logs in at the guest's getty. Cloud images have no console password, so set one through user data (`chpasswd`) to use it; one serial session at a time. *CloudWatch* metrics of a VM instance come from the guest, not from QEMU: the collector asks the EC2 service for a sample, which runs one `guest-exec` that reads `/proc/stat` twice a second apart (`CPUUtilization`, no state between samples), `/proc/meminfo` (`MemoryUsed` = total - available, `MemoryUtilization`), `/proc/net/dev` without `lo` (`NetworkIn/Out`), `/proc/diskstats` for whole disks (`DiskReadBytes/WriteBytes`) and the process count, published under the same `HC/EC2` namespace and `InstanceId` dimension as containers. `/proc` through `guest-exec` was chosen over `guest-get-cpustats` (new in QGA 7.1, not in every image) and QMP statistics (which only see the virtual devices). Samples run beside the collector's tick, one per instance at a time, and publish nothing while the agent is not up. `homecloud backup` still sees the VM container: a backup copies the root volume's qcow2 file, which points at the cached cloud image (the cache volume itself is left out of backups).

**Security groups.** Ingress and egress rules are enforced between the resources of a VPC, not only at the host boundary. Every resource that has security groups (an EC2 instance, an ECS task, an RDS or ElastiCache node, a load balancer, a Lambda environment with a VPC configuration) gets an iptables ruleset rendered from its groups and loaded into *its own network namespace*: ingress is default-deny, a packet is accepted when a rule of one of the resource's groups matches its protocol, port range (ICMP type and code) and source, and replies to accepted connections always flow back (connection tracking, so rules are stateful in both directions). A source is a CIDR or a referenced group ("from sg-app" = from every resource that has sg-app), which HomeCloud resolves to the group members' current addresses inside the VPC. A resource with no groups is in the VPC's default group, which (as in AWS) allows all inbound traffic from its own members. Egress is not filtered while a resource's groups still contain the default allow-all rule; once it is revoked, only the egress rules (plus DNS and the instance metadata service, which are always reachable) let traffic out. A load balancer is a member of its own groups, so its traffic to a target is judged by the target's groups (the target's group must allow the balancer's group), and health checks obey them too. Listener ports of internet-facing balancers, publicly accessible databases and Lambda emulator ports are published on the host whatever the groups say, so traffic from outside the VPC to them is accepted and the groups filter only what comes from inside it.

The rules are loaded by a short-lived helper container that joins the target's namespace with `NET_ADMIN` (`docker run --net container:<id> --cap-add NET_ADMIN`). That is portable: it behaves the same on Linux Docker, Docker Desktop and OrbStack, where containers live in a VM and the host has no view of their firewall, it needs no host root, and the resource itself gets no extra capability and cannot alter its own rules. The helper image (`homecloud/sgfw`) is built locally the first time from a Dockerfile in the repository (Alpine pinned by digest plus the `iptables` package), so the first launch after an upgrade needs network access to build it. Rules live in the namespace, which Docker rebuilds whenever a container starts, so HomeCloud re-applies them on launch, on every container start (it watches Docker's start events, which covers reboot, restart policies and re-creation), when a group's rules change, when a resource's groups change, and when a resource that a group rule refers to appears or disappears; a pass every few seconds catches the rest. Each application is one atomic `iptables-restore`, so a change never opens a gap.

**S3.** HomeCloud runs one MinIO server (`homecloud-s3`) with generated root credentials stored in Secrets Manager, attaches it to every VPC as `s3.internal`, and exposes both the native S3 endpoint (default port 9500) and a management API used by the console and CLI.

**RDS / ElastiCache / DocumentDB.** Each database is a container from the official engine image with a named volume, placed in a subnet with DNS `<id>.rds.internal` (or `.elasticache.internal`). Master credentials are generated into the secret `rds!<id>`. Readiness is probed over TCP inside the container. Snapshots are engine-native dumps (`pg_dumpall`, `mysqldump`, `mariadb-dump`, `mongodump`, RDB files) and restore into a new instance. A background loop takes daily automated backups and prunes them after the retention period.

**Lambda.** Functions run in AWS's official Lambda base images (`public.ecr.aws/lambda/python:3.12`, `nodejs:20`, `java:21`, `ruby:3.3`, `dotnet:8`, `provided:al2023`, …; pulled lazily, for the host's architecture), which contain the runtime and the Runtime Interface Emulator. An *execution environment* is one such container with the code package extracted into `/var/task` and layers into `/opt`, its emulator port published on `127.0.0.1` (environments on isolated VPC networks, where Docker publishes no ports, are called through `docker exec curl` instead). An environment serves one invocation at a time and keeps its state between invocations, like AWS. Each function has a pool of environments across its versions: an invocation reuses an idle environment for the same version and configuration, or starts a new one while the function is below its concurrency limit (reserved concurrency, or 10 per function by default; reservations are carved out of an account limit of 100), briefly queues, and is then throttled (`TooManyRequestsException`). Environments are retired when the configuration changes, after 15 idle minutes, and before their role credentials expire. Functions with an execution role get temporary credentials for it (IAM `AssumeRoleForService`, after `iam:PassRole` and a trust check when the role is set) plus `AWS_ENDPOINT_URL` pointing at HomeCloud, so SDK calls from the function reach HomeCloud with the role's permissions. Function errors come back from the emulator as error objects, timeouts as `Task timed out` (the emulator restarts the runtime). Container output is followed per environment; each invocation's lines (START … REPORT, without the emulator's own diagnostics) go to CloudWatch Logs in `/aws/lambda/<name>`, one stream per environment (`YYYY/MM/DD/[version]<id>`), and the tail is returned for `LogType=Tail`. Metrics (`Invocations`, `Errors`, `Duration`, `Throttles`, `ConcurrentExecutions`) go to `HC/Lambda`. CPU scales with memory as in AWS.

Published versions are immutable snapshots of `$LATEST` (configuration and a copy of the code); aliases point at a version and may route a weighted share of traffic to a second one. Asynchronous invocations (`InvocationType=Event`) are queued in memory and retried after function errors (up to `MaximumRetryAttempts`, default 2, 1 and 2 minutes apart) and after throttles or system errors (until `MaximumEventAgeInSeconds`); the outcome is sent to the configured success/failure destination (SQS, SNS, Lambda, EventBridge) as an AWS invocation record, and failed events to the dead-letter queue. Container-image functions (`PackageType=Image`) run any image built on an AWS base image; ECR URIs (`<account>.dkr.ecr.<region>.amazonaws.com/repo:tag`) map to HomeCloud's registry, and the image is re-pulled on every create and code update (`State`/`LastUpdateStatus` stay `Pending`/`InProgress` meanwhile). Event source mappings poll SQS queues (deleting messages on success, honouring `batchItemFailures`) and DynamoDB streams (the checkpoint advances only after a successful batch; `MaximumRetryAttempts`, `BisectBatchOnFunctionError` and an on-failure destination bound retries). The AWS Lambda REST API (`/2015-03-31/...`, signing name `lambda`) and the native API share the same operations.

**API Gateway / function URLs.** Requests are converted to the API Gateway v2 (HTTP API) payload format, and responses follow the same rules (`statusCode`, `headers`, `body`, `isBase64Encoded`, or a bare value returned as JSON).

**SQS.** Queues keep messages in memory with visibility timeouts, delays, long polling (up to 20 s), FIFO ordering per message group with 5-minute deduplication, and dead-letter queues driven by `maxReceiveCount`. Lambda event source mappings poll queues and delete messages on success (supporting `batchItemFailures`).

**SNS.** Publishing fans a message out to matching subscriptions (filter policies on message attributes) over SQS, Lambda or HTTP(S) with retries.

**EventBridge.** Scheduled rules use AWS `rate()` and six-field `cron()` expressions, checked every minute. Pattern rules match published events using exact values, `prefix`, `anything-but`, `exists` and `numeric` operators. Targets are Lambda functions, SQS queues and SNS topics, addressed by ARN.

**Auto Scaling.** A group owns instances tagged `hc:autoscaling:groupName`. Every 10 s it terminates members that stopped (and launches replacements), launches or terminates (newest first) to reach the desired capacity, spreading launches across its subnets, and registers running members with its target groups. Target-tracking policies compare the group's average `HC/EC2` CPU or memory utilization over the last three minutes with the target, scale out proportionally and scale in one instance at a time, within min/max and after a cooldown.

**EFS.** A file system is a named Docker volume that any number of instances mount at launch (`file_systems` in RunInstances), so they share files like an NFS mount.

**ECR.** HomeCloud runs a Docker Distribution registry (`homecloud-ecr`, loopback port 5500 by default) and manages repositories, tags and deletions through its API. Images pushed with `docker push localhost:5500/...` can be used by ECS task definitions and registered as AMIs.

**ELB.** Each load balancer is an nginx container with a private IP in a subnet (`<name>.elb.internal`); internet-facing listeners are published on the host. HomeCloud renders nginx configuration from listeners, path/host rules and target groups, health-checks every target from inside the VPC on the target group's interval and thresholds, and reloads nginx when targets register, deregister or change health. Upstreams share state across workers for true round robin.

**ACM.** HomeCloud creates a private CA (ECDSA P-256, 10 years) on first use and issues leaf certificates for DNS names and IP addresses; imported certificates are validated against their private key. Keys are encrypted under the master key. HTTPS listeners copy the certificate chain and key into the load balancer container and serve TLS 1.2/1.3 with HTTP/2; renewing a certificate reloads every balancer that uses it. Download the CA (`homecloud acm ca`) and trust it on your devices to avoid browser warnings.

**ECS.** Task definitions are versioned (`family:revision`); secrets listed in a task definition are read from Secrets Manager (optionally a JSON key) and injected as environment variables at launch. A reconciler runs every 5 s: it replaces exited tasks, starts tasks for the current revision one at a time, retires tasks from previous revisions once the new ones are up, and registers/deregisters task IPs with the service's target group. Services are reachable inside the VPC as `<service>.ecs.internal`.

**KMS & Parameter Store.** KMS keys hold versioned AES-256 key material encrypted under the master key; ciphertext blobs embed the key ID and version, so rotated keys still decrypt old data, and the encryption context is bound as AEAD associated data. SecureString parameters are encrypted with a service-managed key (`alias/hc/ssm`) or a customer key, bound to the parameter's ARN.

**Step Functions.** Definitions are Amazon States Language JSON, validated on create. Each execution runs in the server as an interpreter over the state graph with InputPath → Parameters → task → ResultSelector → ResultPath → OutputPath processing, `States.Format`/`JsonToString`/`StringToJson`/`Array` intrinsics, the `$$` context object, retries with exponential backoff, catchers, concurrent Parallel branches and Map iterations. Task resources are Lambda functions (direct ARN or `arn:aws:states:::lambda:invoke`), `arn:aws:states:::sqs:sendMessage` and `arn:aws:states:::sns:publish`. Every transition is recorded in the execution history (`sfn/<execution>.json`); executions interrupted by a restart are marked ABORTED. State machines can be EventBridge targets.

**CloudFormation.** Templates (YAML with short tags, or JSON) are parsed into a dependency graph from `Ref`, `GetAtt`, `Sub` references and `DependsOn`. Each resource type maps onto the service's own create/describe/delete API; resource properties are the API's request fields. The engine calls those routes in-process with the caller's identity (so stacks can do exactly what the caller could), waits for asynchronous resources (instances, databases, load balancers) to become ready, and rolls back on failure. Updates replace changed resources and everything that depends on them; deletes run in reverse order and honour `DeletionPolicy: Retain`.

**Cognito.** Each user pool has its own RSA-2048 signing key (encrypted under the master key) and issues RS256 ID and access tokens with issuer `http(s)://<host>:<port>/cognito/<pool>`; the public JWKS and OpenID discovery documents let any app verify them. Refresh tokens are opaque and stored hashed; global sign-out revokes refresh tokens and every access token issued before it. Application-facing endpoints (`/cognito/<pool>/sign-up`, `/auth`, `/respond`, `/userinfo`, `/change-password`, `/sign-out`) need no IAM credentials; sign-in failures are throttled per user and client IP. API Gateway routes with `authorization: JWT` validate tokens against the API's authorizer pool and pass the claims to the function in `requestContext.authorizer.jwt.claims`.

**Route 53.** A managed CoreDNS server (`homecloud-dns`) is attached to every VPC at the reserved address `base+2` (the S3 endpoint uses `base+3`). New instances, ECS tasks and Lambda environments get it as the upstream of Docker's embedded DNS, so container names (`ip-…internal`, `<db>.rds.internal`) keep resolving while hosted zones are layered on top. Zones are rendered as zone files that CoreDNS reloads within seconds; alias records resolve to a resource's current private IP at render time. Public zones are also served on the host's DNS port (default 8053, UDP and TCP) for LAN clients; private zones answer only clients inside their VPCs.

**CloudWatch.** A collector samples every managed container every 30 s (CPU, memory, network, disk I/O, processes) into namespaces `HC/EC2`, `HC/RDS`, `HC/ElastiCache`; Lambda publishes `HC/Lambda` invocations, errors and duration. Alarms evaluate on each cycle and notify SNS topics or webhooks on state changes.

## Security notes

- The API binds to `127.0.0.1` by default. When exposing it, use TLS (`--tls-cert/--tls-key` or `--tls-self-signed`; the CLI trusts a self-signed certificate through `ca_file` in its credentials).
- HomeCloud needs access to the Docker socket, which is root-equivalent on the host; treat HomeCloud administrators as host administrators.
- Console sign-in is throttled after 10 failures per client IP in 5 minutes. Access-key secrets and session tokens are stored as SHA-256 hashes; passwords as bcrypt; secrets and SecureStrings are encrypted under `master.key` (keep it with your backups, and keep it private).
- The container registry listens on loopback only. MinIO's S3 endpoint and database ports marked public listen on all interfaces and require credentials.
- One Docker host runs one HomeCloud installation; the server refuses to start against another installation's containers.
- User-supplied content (static websites, function URLs, HTTP APIs, inline object views) is served with a `Content-Security-Policy: sandbox` header, because it shares an origin with the console.
- Webhooks (SNS HTTP subscriptions, alarm actions) may not target loopback or link-local addresses, checked again at connect time.
- Delivery targets are authorized when they are configured: an EventBridge rule, SNS subscription, queue trigger, API route or state machine can only reach resources its creator could reach directly.

## Limits and differences from AWS

- Instances are containers unless their AMI is a VM image (see **EC2 VM instances** above): container instances share the host kernel, and their "disk" is the container's writable layer. VM instances are QEMU guests with their own kernel and disk (lifecycle, run-command, the serial terminal, guest metrics, extra volumes, snapshots, images and backups are covered); attaching or detaching a volume reboots the guest, native macOS acceleration is not implemented, and they are emulated (slow) on Docker hosts without `/dev/kvm`.
- Security groups filter traffic between resources of a VPC (see Security groups above) and decide which ports are published on the host. Published ports are still fixed at container creation: an instance whose published ports no longer match its groups is recreated from a snapshot of its disk (ID, private IP, volumes and tags are kept, the same host ports are reused for ports that stay open, processes restart), while changes to filtering apply live, with no restart. Limits of the filtering:
  - Covered: EC2 instances, ECS tasks, RDS and ElastiCache nodes, load balancers, and Lambda environments of functions with a VPC configuration. EFS mount targets carry security groups in the API, but a file system is a Docker volume mounted into the instance and there is no network path to filter, so they are recorded only.
  - Ingress sources that can be matched are IPv4 CIDRs and groups of the same VPC. Prefix lists and IPv6 ranges are recorded but match nothing (VPC networks are IPv4 only), and groups of a peer VPC do not exist (there is no peering). Network ACLs are recorded, not enforced.
  - A new container is reachable for the moment between its start and the first application of its rules (HomeCloud applies them immediately after starting it, before the resource is reported running, but Docker offers no way to start a container with its rules already in place). Connections that were established before a rule was revoked keep flowing until they end, as with AWS's tracked connections; new connections are refused.
  - Egress: the default allow-all rule means no filtering. With custom egress rules, DNS (the VPC resolver) and the metadata service stay reachable; HomeCloud's other endpoints (the S3 endpoint `s3.internal`, the HomeCloud API through `host.docker.internal`) are ordinary destinations that a restrictive egress rule blocks, as reaching AWS APIs would be.
  - The Docker host is an ordinary source: its connections to a container's private address come from the network's gateway address and are accepted only where a rule allows them (ports published to 127.0.0.1); `docker exec` (run-command, terminals, metrics) runs inside the container and is not filtered.
  - Filtering needs Linux containers with netfilter and connection tracking in the container's kernel (every mainstream Docker host has them). If the helper image cannot be built (no network on first use), HomeCloud logs it and resources stay unfiltered until it can.
  - Existing default groups receive AWS's self-referencing inbound rule once, at the first start of this version. Resources in different groups that talked freely before now need a rule between their groups.
- Volume sizes are advisory (Docker volumes are not size-capped).
- HomeCloud has two APIs: the native REST/JSON API (`/api/v1`, used by the console and the `homecloud` CLI) and the AWS wire protocols for the services listed in [aws-compat.md](aws-compat.md), used by the AWS CLI, SDKs and Terraform. Services not listed there are reachable through the native API only.
- HomeCloud runs on one Docker host today.
